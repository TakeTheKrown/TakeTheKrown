# 👑 TAKE THE CROWN

> 2~8인 경쟁형 3D 멀티플레이어 FPS — 왕관을 뺏고, 지키고, 굴려라.

물리엔진이 만들어내는 예측 불가능한 상황에서 왕관 하나를 두고 싸우는 파티 게임입니다.
왕관을 든 플레이어에게 아이템을 명중시키면 **래그돌 상태로 넘어지며 왕관을 떨어뜨립니다.**

## 1. 게임 개요

| 항목 | 내용 |
|---|---|
| 가제 | TAKE THE CROWN |
| 장르 | 3D 1인칭 경쟁 파티 액션 |
| 플레이 인원 | 최소 2명 ~ 최대 8명 |
| 시점 | 1인칭 (FPS) |
| 플랫폼 | PC (Windows 우선) |
| 핵심 재미 | 물리엔진 기반의 의도치 않은 코미디 + 왕관 쟁탈의 긴장감 |
| 맵 | 테마별 4종 이상, 추후 **맵 에디터** 지원 |

### 한 줄 컨셉

> 맵 중앙 높은 곳에 왕관이 있다. 2분 뒤 왕관을 들고 있는 사람이 이긴다.
> 문제는, 이 게임의 **모든 것이 물리엔진으로 굴러다닌다**는 것이다.

## 2. 핵심 규칙

### 2-1. 매치 구조

```
매치 (Match)
 └─ 게임 (Game) × N회        ← 설정 가능, 기본 1
     └─ 라운드 (Round) × M회  ← 설정 가능, 기본 3
         ├─ 본 라운드 : 120초
         └─ 서든데스   : 60초 (조건부 발동)
```

### 2-2. 라운드 타임라인

| 시점 | 이벤트 |
|---|---|
| `T = 0s` | 라운드 시작. 왕관이 맵 중앙 고지대에 하이라이트된 채 스폰. **1차 아이템 드랍** |
| `T = 60s` | **2차 아이템 드랍** |
| `T = 100~105s` | 왕관 소지자 **전역 하이라이트 시작** (잔여 15~20초, 튜닝 대상) |
| `T = 120s` | 라운드 종료 판정 |

### 2-3. 승리 판정

- 라운드 종료 시점에 **왕관을 소지한 플레이어가 해당 라운드 우승**
- 아무도 왕관을 들고 있지 않다면 → **서든데스** 진입
  - 자기장(Shrinking Zone)이 수축하며 활동 범위를 좁힘
  - 아이템 드랍 빈도 증가
  - 60초 동안 진행하며, 먼저 왕관을 획득해 유지하는 쪽이 우승
  - ※ 서든데스에서도 미결이면 **홀드 누적 시간이 가장 긴 플레이어** 우승 (폴백 규칙)

### 2-4. 왕관 (Crown)

| 규칙 | 내용 |
|---|---|
| 획득 | 왕관에 접촉(Trigger)하면 즉시 소지. 별도 상호작용 키 없음 |
| 소지 상태 | 머리 위에 부착. 소지자는 이동 속도에 **소폭 페널티** (튜닝 대상) |
| 강제 드랍 | 소지자가 **래그돌 상태**가 되면 왕관이 물리 오브젝트로 튕겨 나감 |
| 하이라이트 | 라운드 종료 15~20초 전부터 소지자의 실루엣이 **벽 너머로도 보임** |
| 재획득 쿨다운 | 드랍 직후 0.5~1초간 이전 소지자는 재획득 불가 (튜닝 대상) — 무한 재획득 방지 |

> 하이라이트 규칙의 목적: 왕관 소지자가 구석에 숨어서 시간만 버티는 **캠핑 플레이를 원천 차단**하고,
> 라운드 후반에 반드시 교전이 일어나도록 강제한다.

### 2-5. 아이템 (Item)

| 규칙 | 내용 |
|---|---|
| 스폰 시점 | 라운드 시작 시 1회, 라운드 중간(60초) 1회 |
| 스폰 위치 | 서버가 사전 정의된 스폰 포인트 중 **랜덤 선택** |
| 분산 제약 | 동시에 스폰되는 아이템끼리 **최소 거리 이상** 유지 (뭉쳐서 스폰 금지) |
| 사용 효과 | 왕관 소지자에게 명중 시 → **래그돌 전환 → 왕관 드랍** |
| 투척 판정 | 아이템을 **다 쓰고 던져서 맞춰도 동일하게 왕관 드랍 판정** |
| 물리 적용 | 아이템 자체가 Rigidbody. 바닥에 굴러다니고, 경사면에서 미끄러짐 |

### 2-6. 점수 시스템

라운드 종료 시 아래를 합산해 **매 라운드마다 랭킹**을 산출합니다.

```
라운드 점수 = (왕관 홀드 시간 × 홀드 계수)
            + (아이템 명중 횟수 × 명중 보너스)
            + (라운드 우승 보너스)
```

- 홀드 시간은 **서버 틱 기준으로 누적** (클라이언트 시간 신뢰 금지)
- 각 계수는 `GameRuleConfig` ScriptableObject에서 조정하며, 밸런싱 과정에서 계속 변경됩니다
- 매치 최종 순위 = 전체 라운드 점수 합계

### 2-7. 물리 적용 범위

> **원칙: 맵 베이스 지오메트리를 제외한 거의 모든 것에 물리를 적용한다.**

| 대상 | 물리 |
|---|---|
| 맵 지형/구조물 (베이스) | ❌ Static Collider |
| 왕관 | ✅ Rigidbody (미소지 시) |
| 아이템 | ✅ Rigidbody |
| 플레이어 | ✅ 평상시 CharacterController → 피격 시 Ragdoll 전환 |
| 소품/장식물 | ✅ Rigidbody (성능 예산 내에서) |

## 4. 네트워크 스택 선정 (검토 결과)

### 4-1. 비교표

| 기준 | Netcode for GameObjects | Photon Fusion 2 | Mirror |
|---|---|---|---|
| 비용 | 무료 (Unity 공식) | 무료 100 CCU (1앱 한정), 이후 유료 | 무료 (MIT) |
| Unity 6 통합 | ★★★ 공식 패키지, 템플릿 기본 | ★★ 별도 SDK | ★★ 별도 패키지 |
| **물리 예측/롤백** | ✖ 내장 없음 | ★★★ 내장 (Fusion의 최대 강점) | ✖ 직접 구현 |
| 서버 권위 물리 | `NetworkRigidbody` 제공 | 제공 | 제공 |
| 러닝 커브 | 낮음 | 높음 | 중간 |
| 8인 규모 적합성 | 충분 | 충분 (과잉) | 충분 |
| 한국어/영어 자료 | 매우 많음 (Boss Room 샘플) | 보통 | 많음 |
| 상용 서비스 종속 | 없음 | 있음 | 없음 |

### 4-2. 결론: **NGO 2.x로 시작**

**근거**

1. 이미 Unity의 **3D Multiplayer 템플릿**으로 프로젝트를 생성했으므로 초기 셋업 비용이 0에 가깝다.
2. 팀 4명이 **동시에 네트워킹을 학습**해야 하는 상황에서, 공식 문서와 Boss Room 레퍼런스가 있는 NGO의 학습 비용이 가장 낮다.
3. 동시 접속 8명은 어떤 스택으로도 무리 없는 규모다. Fusion의 예측/롤백은 20~30인 이상 고속 슈터에서 진가를 발휘하며, **본 프로젝트의 병목이 아니다.**
4. 외부 서비스 CCU 제한 / 계정 문제에서 자유롭다.

### 4-3. ⚠️ NGO 사용 시 반드시 알아야 할 제약

공식 문서 기준, NGO의 물리 동기화에는 다음 제약이 있습니다. **이 프로젝트는 물리가 핵심이므로 특히 중요합니다.**

- **비권위(non-authoritative) 클라이언트에서는 Rigidbody가 kinematic 상태입니다.**
  → 클라이언트에서 네트워크 Rigidbody 간 **Collision 이벤트가 발생하지 않습니다.** (Trigger는 발생)
  → **모든 충돌 판정은 서버에서 처리하고, 결과만 RPC로 클라이언트에 전파**해야 합니다.
- **Rigidbody용 클라이언트 예측/롤백이 내장되어 있지 않습니다.**
  → 아이템 투척 → 명중 → 래그돌까지 RTT만큼의 지연이 시각적으로 드러납니다.
  → 완화책: 클라이언트에서 **투척 궤적과 히트 이펙트를 즉시 로컬 재생**(예측)하되, **왕관 드랍 여부의 최종 판정은 서버**가 내리고 어긋나면 서버 상태로 보정합니다.
- Rigidbody 값 변경은 `FixedUpdate` **이후**에 적용해야 타이밍 문제가 없습니다.

### 4-4. 탈출구 확보 (중요)

프로토타입 단계에서 **물리 체감 지연이 게임 재미를 해칠 정도**로 판명되면 Fusion 2로 전환할 수 있습니다.
전환 비용을 낮추기 위해 다음 규약을 지킵니다.

> **게임 로직(라운드 상태머신, 점수 계산, 아이템 효과 규칙)은 NGO API에 직접 의존하지 않는다.**
> 네트워크 호출은 `Scripts/Networking` 레이어의 인터페이스를 통해서만 접근한다.

이 판단은 **Phase 2 종료 시점에 팀 전체가 함께 내립니다.** 그 전까지는 NGO로 직진합니다.

## 5. 아키텍처 원칙

### 5-1. 서버 권위 (Server Authority)

> **"클라이언트는 아무것도 결정하지 않는다. 보여주기만 한다."**

서버가 단독으로 결정하는 것:

- 왕관의 소유자 (`holderClientId`)
- 아이템 스폰 위치와 시점
- 아이템 명중 / 래그돌 전환 판정
- 라운드 타이머, 라운드/게임 종료
- 점수 및 홀드 시간 누적
- 자기장 반경과 수축 진행도

클라이언트가 하는 것: 입력 전송, 시각적 예측, 렌더링, UI.

### 5-2. 왕관 소유권 모델

`NetworkObject`의 Ownership을 넘기는 대신 **서버 권위 + 상태 변수** 방식을 사용합니다.

```
Crown (NetworkObject, 서버 소유 고정)
 ├─ NetworkVariable<ulong> HolderClientId   // ulong.MaxValue = 무소유
 ├─ 소지 중  : Rigidbody.isKinematic = true, 소지자 헤드 본에 부착
 └─ 무소유   : Rigidbody 활성화, 물리로 굴러다님
```

Ownership 이전은 8인 환경에서 경합(race) 상황을 만들기 쉽고 디버깅이 어렵습니다.
`NetworkVariable` 하나로 상태를 표현하면 **단일 진실 공급원(single source of truth)** 이 유지됩니다.

### 5-3. 래그돌 처리

```
[서버] 명중 판정 → Ragdoll 상태 진입 결정 → NetworkVariable 갱신 + ClientRpc 브로드캐스트
[클라] RPC 수신 → 로컬에서 Ragdoll 활성화 (시각 표현은 각자 시뮬레이션)
[서버] 래그돌 루트 본의 위치만 동기화 → 클라 위치 보정
```

전신 본을 모두 동기화하면 대역폭이 폭발합니다. **루트 위치·회전만 권위 동기화**하고
나머지 관절은 각 클라이언트가 로컬에서 시뮬레이션합니다. 파티 게임 특성상 관절 불일치는 허용 가능합니다.

### 5-4. 아이템 스폰 분산

서버는 맵에 사전 배치된 `ItemSpawnPoint` 집합에서 다음 규칙으로 선택합니다.

1. 후보 스폰 포인트를 셔플
2. 이미 선택된 지점과의 거리가 `minSpawnDistance` 미만이면 기각
3. 필요한 개수를 채울 때까지 반복, 후보 소진 시 제약을 단계적으로 완화

시드는 서버가 생성하며, 재현 가능한 테스트를 위해 **시드를 로그에 남깁니다.**

### 5-5. 설정 데이터는 ScriptableObject로

라운드 시간, 아이템 드랍 타이밍, 점수 계수, 하이라이트 시작 시점 등 **모든 밸런싱 수치는 코드에 하드코딩하지 않고**
`GameRuleConfig`, `ItemDefinition`, `MapDefinition` 등의 ScriptableObject에 둡니다.

- 밸런싱 변경에 코드 리뷰가 필요 없어지고
- 팀원끼리 **코드 파일 충돌이 줄어듭니다** (매우 중요)

## 6. 개발 환경 세팅

### 6-1. 요구 사항

- Unity Hub + **Unity 6 LTS** (정확한 버전은 `ProjectSettings/ProjectVersion.txt` 확인 — 팀 전원 동일해야 함)
- Git 2.40+
- **Git LFS** (`git lfs install`)
- IDE: JetBrains Rider 또는 Visual Studio 2022

### 6-2. 최초 클론

```bash
git lfs install
git clone <repo-url>
cd take-the-crown
git lfs pull
```

> `git lfs pull` 을 빼먹으면 모델과 텍스처가 **깨진 포인터 파일**로 열립니다. 반드시 실행하세요.

### 6-3. Unity 에디터 필수 설정

`Edit → Project Settings` 에서 아래를 확인합니다. **팀 전원 동일해야 하며, 이미 커밋되어 있으므로 임의 변경 금지입니다.**

| 설정 | 값 | 이유 |
|---|---|---|
| Editor → Version Control | **Visible Meta Files** | `.meta` 파일이 있어야 참조가 유지됨 |
| Editor → Asset Serialization | **Force Text** | 씬/프리팹을 텍스트로 저장해야 Git diff·머지 가능 |
| Editor → Enter Play Mode | Reload Domain 옵션 팀 합의 후 통일 | 반복 테스트 속도 |

### 6-4. 로컬 멀티플레이 테스트

Unity의 **Multiplayer Play Mode** 패키지를 사용하면 에디터 하나로 여러 클라이언트를 띄울 수 있습니다.
빌드해서 여러 개 실행하는 방식보다 반복 속도가 훨씬 빠릅니다.

`Window → Multiplayer → Multiplayer Play Mode` 에서 Virtual Player 2~3개를 활성화해 테스트하세요.

지연 상황 재현은 **Network Simulator** 로 인위적인 latency/packet loss를 걸어 확인합니다.
**"내 로컬에서는 잘 되는데"는 멀티플레이 개발에서 아무 의미가 없습니다.**

## 7. 프로젝트 폴더 구조

```
Assets/
├─ _Project/                 # 우리가 만드는 모든 것은 여기 안에
│  ├─ Art/
│  │  ├─ Models/  Materials/  Textures/  VFX/  Audio/
│  ├─ Prefabs/
│  │  ├─ Player/  Crown/  Items/  Map/  UI/
│  ├─ Scenes/
│  │  ├─ Bootstrap.unity        # 진입점
│  │  ├─ Lobby.unity
│  │  ├─ Maps/                  # Map_XXX.unity
│  │  └─ Sandbox/               # 개인 테스트 씬 (Sandbox_이름.unity)
│  ├─ ScriptableObjects/
│  │  ├─ GameRuleConfig/  ItemDefinition/  MapDefinition/
│  ├─ Scripts/
│  │  ├─ Core/         # 게임 루프, 라운드 상태머신, 점수, 랭킹
│  │  ├─ Networking/   # 세션, 매치메이킹, 네트워크 추상화 레이어
│  │  ├─ Player/       # 이동, 1인칭 카메라, 래그돌
│  │  ├─ Crown/        # 왕관 상태, 부착, 하이라이트
│  │  ├─ Items/        # 아이템 정의, 스폰, 투척, 명중 판정
│  │  ├─ Map/          # 스폰 포인트, 자기장, (추후) 맵 에디터
│  │  ├─ UI/           # HUD, 로비, 스코어보드
│  │  └─ Shared/       # 공용 유틸 — 수정 시 팀 합의 필요
│  └─ Settings/        # URP 에셋, 입력 액션
└─ ThirdParty/         # 외부 에셋 (수정 금지, 업데이트는 담당자만)
```

**규칙**

- 외부 에셋은 반드시 `ThirdParty/` 아래에 격리합니다. `_Project/`와 섞으면 에셋 업데이트 시 우리 코드가 날아갑니다.
- `Scripts/` 각 하위 폴더에는 **Assembly Definition(.asmdef)** 을 둡니다.
  컴파일 시간이 줄고, 모듈 간 의존 방향이 강제되어 **다른 사람 코드에 무단으로 손대기 어려워집니다.**
- 의존 방향은 한 방향으로만: `UI → Core → Networking/Shared`. 역방향 참조는 PR에서 거부합니다.
- 개인 실험은 `Scenes/Sandbox/Sandbox_<이름>.unity` 에서만 합니다.

## 8. 팀 구성과 담당 모듈

각자 **자기 모듈의 오너**입니다. 오너의 파일을 다른 사람이 임의로 수정하거나 삭제할 수 없습니다.
자세한 규칙은 [CONTRIBUTING.md](./CONTRIBUTING.md) 를 반드시 읽어주세요.

| 담당 | 이름 | 주요 모듈 | 소유 경로 |
|---|---|---|---|
| 네트워크 / 게임 루프 | (미정) | 세션·호스팅, 라운드 상태머신, 게임 진행 | `Scripts/Networking`, `Scripts/Core` |
| 플레이어 / 물리 | (미정) | 1인칭 이동·카메라, 래그돌, 물리 튜닝 | `Scripts/Player` |
| 왕관 / 아이템 / 점수 | (미정) | 왕관 로직, 아이템 시스템, 점수·랭킹 | `Scripts/Crown`, `Scripts/Items` |
| 맵 / UI | (미정) | 레벨 디자인, 자기장, HUD·로비 UI | `Scripts/Map`, `Scripts/UI`, `Scenes/Maps` |

> 이름을 채우고 커밋해 주세요. 담당은 고정이 아니며, 페이즈마다 팀 회의에서 조정할 수 있습니다.

## 10. 용어 사전

문서·코드·커밋 메시지에서 **동일한 용어**를 사용합니다.

| 한국어 | 코드 표기 | 정의 |
|---|---|---|
| 매치 | `Match` | 여러 게임을 묶은 전체 세션 |
| 게임 | `Game` | M개의 라운드로 구성된 단위 |
| 라운드 | `Round` | 120초 단위의 최소 승부 단위 |
| 왕관 | `Crown` | 승리 조건 오브젝트 |
| 소지자 | `Holder` | 현재 왕관을 들고 있는 플레이어 |
| 서든데스 | `SuddenDeath` | 무승부 시 60초 연장 모드 |
| 자기장 | `ShrinkingZone` | 서든데스에서 수축하는 활동 영역 |
| 래그돌 | `Ragdoll` | 피격 시 물리 인형 상태 |
| 홀드 시간 | `HoldTime` | 왕관 소지 누적 시간 (점수 산정 기준) |
| 드랍 | `Drop` | 왕관이 소지자에게서 이탈하는 것 |
